# PR レビューコメントへの対応

## 手順

### 1. PR を特定する

現在のブランチから PR 番号と URL を取る。PR がなければ、番号か URL をユーザーに求める。`url` から読み取れる `{owner}/{repo}` は、コメントを取るときと返信するときに使う。

```bash
gh pr view --json number,url
```

### 2. レビューコメントを取る

行に付いたスレッド・レビュー全体の本文・PR の会話のコメントを、1 回の GraphQL で取る。REST API のレビューコメントには、解決済みかどうかの情報が含まれないため。GraphQL は `gh api graphql` で直接呼ばず、クエリを固定したスクリプトで呼ぶ。`gh api graphql` は書き込みもできるので毎回確認を求める設定にしてあり、このスクリプトだけを `allowed-tools` で確認なしに実行できるようにしているため。`allowed-tools` の許可はこのスキルを呼び出したターンの間だけ効くので、最初のターンのうちに、パスを書き換えずに実行する。

```bash
${CLAUDE_SKILL_DIR}/scripts/fetch_comments.sh {owner}/{repo} {pr}
```

- まず全コメントを取る。ユーザー名で絞り込まない
- outdated のスレッド (コードの変更で行がずれたもの) も除外しない。指摘が今のコードにも当てはまるかを、この節の末尾の手順で位置を特定してから確かめる
- スレッド内の返信も読み、すでに返信や合意が済んでいるかを判断する
- レビュー全体の本文と会話欄のコメントのうち、指摘を含まないもの (承認の一言、CI の結果を知らせる bot のコメントなど) と PR の作者のコメントは、分析の対象から外す。作者のコメントは判断材料として読む
- 取得の上限はスレッド 100 件、1 スレッドあたりのコメント 50 件、レビュー全体の本文・会話のコメントは各 100 件。`threadCount`・`reviewCount`・`commentCount` が上限を超えていたらユーザーに伝える

outdated のスレッドの位置は、スクリプトが返す `line`、`startLine`、`originalLine` の順に見て、今のコードと合う行を探す。どれも合わなければ、コメント中のシンボルや特徴的な語で同じファイルを 1 回検索する。見つからなければ「対象のコードがない」と記録し、別のファイルに移った示唆があればユーザーに聞く。

### 3. 分析する

レビュアーの種類で分ける。

- Copilot (`author == "copilot-pull-request-reviewer"`)
- 自動ツール (`type == "Bot"` で Copilot 以外。`github-actions` など)
- チームメンバー (`type == "User"`)

各コメントについて、必要に応じて該当コードを読み、次を分析する。

1. 要約: 何を提案しているか (1〜2 行)
2. 評価: 妥当性 (妥当 / 不適切 / 議論の余地あり)、重要度 (致命的 / 重要 / 推奨 / nitpick)、影響範囲 (大 / 中 / 小 / 些細)
3. 推奨: 対応すべきか (はい / いいえ / 検討)
4. 理由: この推奨の根拠

分析で守ること:

- 自動ツールのコメントでも、妥当性を批判的に評価する
- 同じ投稿者が同じ前提で付けた指摘は、まとめて検証する。1 件の前提が誤りなら、ほかの指摘も同じ誤りを含んでいないか疑う
- 対応を勧める指摘と同じ問題が PR 内のほかの箇所にないかを確かめ、あれば要約に書き添える
- 稀なケースの指摘では、起きやすさ・影響・修正コスト (足す分岐・状態・抽象化) を比べ、「そのまま + 説明 → エラーや注記 → 最小のガード → 完全な修正」の順で最小の対応を選ぶ。守るコードより大きくなる修正は見送り、理由にその旨を書く。bot の指摘で過剰な防御コードが増えるのを防ぐため
- 推奨を「いいえ」にする理由は、次のどれに当たるかで書く。理由の種類が揃うと、ユーザーが判断しやすいため
  - 指摘が成り立たない (根拠を添える)
  - コードが変わって当てはまらない
  - 直すと悪くなる (規約違反、不要な防御、エラーの握りつぶし)
  - PR の目的の範囲外
  - 直す利益がない
  - 意図的な設計で、合理的な意見の相違がある (意図を示す証拠を添える)
  - 質問であり、答えるだけでよい
- 複数の対応方法があるときは、それぞれのメリット・デメリットを示す
- 分析は簡潔かつ技術的に正確に書く

分析結果は表で提示する。「同上」のように他のコメントを参照するものや、同じ種類の指摘の繰り返しは、パターンを説明する最初の 1 件の直後に並べ、残りはファイルと行の順にする。ユーザーが同じ判断を繰り返さずに済むため。URL の列は、表の要約から原文に飛べるようにするためのもの。

| No. | ファイル:行 | レビュアー | 要約 | 評価 | 推奨 | URL |
|---|---|---|---|---|---|---|
| 1 | service.js:42 | Copilot | エラーハンドリング追加 | 妥当、重要、中 | はい | <https://github.com/o/r/pull/12#discussion_r1001> |
| 2 | utils.ts:10 | github-actions | 型アノテーション追加 | 妥当、推奨、小 | はい | <https://github.com/o/r/pull/12#discussion_r1002> |
| 3 | component.tsx:55 | alice | useMemo で最適化 | 議論の余地あり、推奨、中 | 検討 | <https://github.com/o/r/pull/12#discussion_r1003> |

分析を提示したら止まり、どのコメントに対応するかはユーザーの指示を待つ。分析と同じターンで質問しない。明示的な指示があるまで実装に着手しない。

### 4. 修正する

承認された各コメントについて:

1. 該当ファイルの関連箇所を読む
2. 変更する
3. プロジェクトのフォーマッターやリンターがあれば実行する
4. `commit` スキルで、1 つのレビューコメントにつき 1 つのコミットを作る。コミットハッシュを返信に書けるようにするため

すべての修正を終えたら、作成したコミットの一覧を提示して止まる。push はユーザーの指示を受けてから実行する。

### 5. push の後に返信する

コミットハッシュはリモートにないとレビュアーが辿れないので、返信は push の後に行う。PR 本文の更新や、PR の変更内容を指す issue コメントの投稿も push の後に行う。読み手が本文を見た時点でリモートのコードと一致しない期間を作らないため。残作業を並べるときは「コード変更 → セルフレビュー → push → PR 本文 → issue コメント → 返信」の順にし、push を文書の前に置く。

#### 5.1 下書きのレビューを確かめる

返信の前に、自分の下書きのレビュー (PENDING) が残っていないかを確かめる。残っていると返信の API が失敗するため。

```bash
gh api repos/{owner}/{repo}/pulls/{pr}/reviews --jq '.[] | select(.state == "PENDING") | {id, body}'
```

残っていれば、ID・本文・インラインコメントの件数をユーザーに示して、破棄してよいかを確かめる。破棄するとユーザーが手で書いたコメントも消え、戻せないため。了承を得たら削除し、破棄しないなら GitHub の画面で送信してもらい、済んだと言われてから返信する。

```bash
gh api repos/{owner}/{repo}/pulls/{pr}/reviews/{review_id}/comments --jq 'length'
```

```bash
gh api --method DELETE repos/{owner}/{repo}/pulls/{pr}/reviews/{review_id}
```

#### 5.2 返信文を提示して承認を得る

対応したスレッドごとに返信文 (対応内容 1 行とコミットハッシュ) を一覧で提示し、承認を得てから投稿する。

- 返信文の 1 行目には `<sub>🤖 Claude <モデル名> による返信</sub>` を書き、空行を挟んで対応内容を続ける。返信はユーザーのアカウントで投稿されるので、読む前に Claude が書いたものだと分かるようにするため。`<モデル名>` には現在の会話のシステムプロンプトに記載された Claude のモデル表示名 (例: `Opus 5`、`Sonnet 5`) を入れ、1M context 版などのサフィックスがあれば併記する
- 一覧には、スレッドを解決するかの列を付け、既定は「しない」にする。チームによってはレビュアーが解決する慣習があるため
- 対応しなかったコメントに返信するかどうかは、ユーザーの指示に従う。返信するときは、返信先の文を引用し、次のどれかの形で書く
  - 対応しない: 根拠 (例: null チェックは 85 行目に既にある)
  - 見送り: 直したときの具体的な害
  - この PR の範囲外: PR の目的と、別の変更にする理由

#### 5.3 投稿する

- 返信先はスレッドの先頭コメントの `id` にする。GitHub の API は返信への返信を受け付けないため
- 本文は `{"body": "<返信文>"}` の JSON ファイルに書き、`--input` で渡す。返信文に含まれる引用符をコマンドの引用と干渉させないため

  ```bash
  gh api --method POST repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies --input <JSON ファイルの絶対パス>
  ```

- ユーザーが「する」を選んだスレッドだけ、返信の後に手順 2 の `threadId` で解決する

  ```bash
  gh api graphql -f threadId='<threadId>' -f query='mutation($threadId:ID!){resolveReviewThread(input:{threadId:$threadId}){thread{isResolved}}}'
  ```

- レビュー全体の本文と会話欄のコメントにはスレッドがないので、返信が要るときは `gh pr comment --body-file <ファイル>` で PR に投稿する。この返信にも同じ署名を付ける
- ユーザーの指示があれば、対応した人間のレビュアー (bot と自分を除く) にレビューを再依頼する。すでに依頼中の人は飛ばす

  ```bash
  gh api --method POST repos/{owner}/{repo}/pulls/{pr}/requested_reviewers -f 'reviewers[]=<login>'
  ```

- 投稿後は次のステップ (例: レビュー再依頼) を提案する

## エラーのとき

- `gh api` が失敗したら、エラーを説明して直し方を示す
- コメントが参照しているコードがすでにないときは、その旨を分析に書く
- コメントの意図が分からないときは、ユーザーに確認する
