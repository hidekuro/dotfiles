# Commit

## 目指すもの

コミットメッセージは、変更の重さに見合った簡潔さで書く。過剰な説明・場所の明示・不要な本文は、履歴を読む人の時間を奪う。書く量は変更の粒度で決め、迷ったら短いほうにする。足りなければ読み手は diff を見るか聞けるが、長い本文は読まれない。

## 手順

### 1. 変更とリポジトリの慣例を把握する

次を 1 つずつ実行する。

- `git status` と `git diff` で変更の全体像を見る
- `git log --oneline -10` で、言語・接頭辞・長さの慣例を見る
- commitlint の設定ファイルと CONTRIBUTING があれば読む。コミットメッセージの規約があれば、この文書の「書き方」より優先する

### 2. コミット単位に分ける

- 論理的なまとまりで分ける。目的が独立している変更は別のコミットにする
- 1 ファイルに複数の目的の変更が混ざっているときは、ハンク単位に分けず 1 コミットにし、目的を本文に箇条書きで並べる。`git add -p` は対話的で Bash ツールから扱えないため
- 分け方に迷う変更は、分け方の案を示して聞く

### 3. メッセージ案を書き、規則に照らして削る

「書き方」に従って下書きし、示す前に次の問いで見直す。1 つでも「はい」なら、その行を消すか短くする。

- 1 行目に当てる問い
  1. diff を見れば分かることを書いているか (ファイル名、変更点の列挙、処理内容の説明)
  2. 変更の種類の一語か動機の 1 文で足りるのに、理由や経緯まで続けていないか
- 本文の各行に当てる問い (`Co-Authored-By` の行は除く)
  1. diff を見れば分かることを書いているか
  2. 1 行目と diff から読み取れない背景・制約・あえてしない理由、のどれでもないか

書く時点では「背景が要る」と思えても、読み直すと diff の言い換えであることが多い。

### 4. 案を示してターンを終える

各コミットの対象ファイルとメッセージ案を、チャットの本文に示してターンを終える。AskUserQuestion は使わない。質問の画面を出すと、その前に出した本文が隠れて読めないことがあるため。

### 5. 返事を受けてコミットする

- 「ok」「はい」のような短い肯定なら、コミットごとに次を 1 つずつ実行する
  - `git add <対象のパス>` でステージする
  - `git diff --cached -- <対象のパス>` で、秘密情報・デバッグ出力・無関係な整形差分が混ざっていないかを見る。混ざっていれば外して案を示し直す。パスで絞るのは、ユーザーが事前にステージしていた別のファイルを検査の対象にしないため
  - 次の形でコミットする。メッセージは単一引用符の heredoc で渡す。`$` やバッククォートをシェルに展開させないためで、hook もこの形式を読み取れる。パスを付けるのは、ユーザーが事前にステージしていた無関係なファイルを巻き込まないため

    ```bash
    git commit -m "$(cat <<'EOF'
    <メッセージ>
    EOF
    )" -- <対象のパス>
    ```

  - 依頼に push が含まれていれば、続けて `git push` する
- それ以外の返事は修正の指示として扱い、直した案を示し直す
- コミットの後に `git status --porcelain -- <対象のパス>` を見て、コミットしたパスに差分が残っていれば、hook がファイルを書き換えたものとして報告する

### 6. hook で失敗したら

失敗したコミットは作られていないので、`--amend` は直前の別のコミットを書き換えてしまい、`--no-verify` は検査を素通りさせる。どちらも使わず、次のようにコミットし直す。

- hook が修正済みのメッセージを示したときは、その文面でコミットし直す
- それ以外で、メッセージやファイルを直す必要があるときは、直した案や差分を示し直し、手順 5 と同じく返事を待ってからコミットし直す

## 書き方

変更の重さで 3 段階に分ける。

### 些末な変更は一語

書式整形・typo 修正・インデント調整・コメントの言い回し直しなど、diff を見れば意図も理由も自明なもの。変更の種類を表す一語だけにし、動機も場所も本文も書かない (`Co-Authored-By` は付ける)。

- 例: `書式整形`、`typo 修正`、`コメント修正`

判断を含む変更はここに入れない。rename やファイル移動は「何を何に」は diff で分かっても「なぜその名前・場所か」が読めないことが多いので、次の段階で意図を 1 行書く (例: `リスト取得メソッドの命名を find_ 始まりに統一`)。

### 通常の変更は 1 行で動機

「なぜ / 何のためにしたか」を 1 行で書く。ファイル名や変更点の列挙のような、差分から読み取れることは繰り返さない。

- 悪い: `○○メソッドにエラーハンドリングを追加`
- 良い: `○○処理が失敗したときにユーザーにエラーを伝えられなかった問題を修正`

### 背景が要るときだけ本文を足す

本文 (3 行目以降) は原則不要。1 行目と diff から読み取れない背景・制約・「あえてこうしない理由」があるときだけ書く。その背景が README やコードに既にあるなら重複なので書かない。

例外として、破壊的変更・セキュリティ修正・データ移行・revert では、1 行目で済みそうでも本文に背景 (何が壊れるか、何を戻すか) を書く。履歴を辿る人がその種類の変更では理由を必ず探すため。この 4 種以外は、手順 3 の見直しで消す側に倒す。

### 書かないこと

- 差分の列挙。「何を変更したか」の羅列・箇条書き。一語コミットの種類名はこれに当たらない
- セッション・計画の文脈に依存する語。「残りの」「先行変更に続き」「フェーズ 2」など、前の PR や会話を知らないと通じない語。各コミットは単体で意味が通るようにする
- ユーザーのプロンプトや個人ルールを指す語。「規約に合わせる」「ルール通りに修正」など。他人に通じないので、何をしたかを具体語で書く
- 顧客名・組織名・問い合わせの内容。履歴に残り続け、リポジトリを公開すれば誰でも読めるため
- リポジトリの外のローカル設定をどう変えたか。「`~/.claude/settings.json` に許可ルールを足した」のような、そのマシンでの作業メモ。コミットに含まれず、ほかの環境では確かめようがないため。その設定が前提になる変更では、前提をリポジトリの中の文書 (SKILL.md や README) に書く
- 手動改行での折り返し。1 文の途中で改行せず、72 桁などで折り返さない (GitHub やエディタが表示幅で折り返す)。1 文が長すぎるとき (150 文字を目安) は文を分割するか、ハイフン (`-`) で始まる箇条書きにする

動機の推論元として会話の文脈は使ってよいが、文脈に依存する語を本文に残さない。文脈からも動機が分からないときはユーザーに確認する。

### 形式

```text
<1 行目: 些末なら種類の一語、通常なら変更の動機・目的>

<3 行目以降: コードから読み取れない背景・制約 (必要な場合のみ)>

Co-Authored-By: <モデル名> <noreply@anthropic.com>
```

- 1 行目は「である調」 (レポート調) で書く
- 並列構造があるときは、ハイフン (`-`) で始まるリストにする
- `Co-Authored-By` トレーラーは、粒度にかかわらず末尾 (空行の後) に付ける。モデル名はシステムコンテキストから読み取った実際の名前 (例: `Claude Fable 5.1`、`Claude Opus 4.8`) を使う

## 例

**些末な変更** (それぞれ別のコミットのメッセージ。一語だけ):

- `書式整形`
- `typo 修正`
- `コメント修正`

**通常の変更** (1 行だけ。これが基本形):

```text
○○処理が失敗したときにユーザーにエラーが伝わらなかった問題を修正

Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>
```

**背景が要るとき** (例外的):

```text
ユーザー増加による応答遅延を解消するためキャッシュを導入

ユーザー数増加により応答時間が 3 秒を超えるケースが発生。頻繁にアクセスされるデータを Redis でキャッシュすることで平均応答時間を 500ms 以下に短縮する。

Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>
```
