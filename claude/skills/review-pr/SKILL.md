# PR コードレビュー実施

## ワークフロー

### 1. PR 番号の取得

PR 番号や PR URL の指定がなければ、現在のブランチから PR 番号を取得する:

```bash
gh pr view --json number --jq '.number'
```

PR が存在しない場合は、ユーザーに PR 番号または PR URL の入力を求めます。

### 2. PR 情報の取得

#### 2.1 PR 本文と基本情報の取得

```bash
gh pr view {pr_number} --json title,body,author,baseRefName,headRefName,url,additions,deletions,labels
```

`url` から読み取れる `{owner}/{repo}` は、5 でプレビューを作るときと、レビューを投稿するときに使う。PR が現在のディレクトリとは別のリポジトリにある場合は、`gh pr view`・`gh pr diff`・`gh pr checks` に `-R {owner}/{repo}` を付ける。

#### 2.2 依存関係更新 PR の判定

取得した情報から、PR が renovate / dependabot による依存関係更新かを判定する。次のいずれかに該当する場合、後述の「依存関係更新 PR のレビュー」フローに分岐する:

- `author.login` が `renovate[bot]`、`dependabot[bot]`、`renovate-bot` などの bot アカウント
- `labels[].name` に `dependencies`、`renovate`、`dependabot` などが含まれる

判定が真の場合は、通常のコードレビュー観点ではなく、依存パッケージ更新の安全性評価を行う。専用フローの詳細は `references/dependency-update-review.md` を読んで実施する。

#### 2.3 変更ファイル一覧の取得

```bash
gh pr diff {pr_number} --name-only
```

#### 2.4 コード差分の取得

ファイル数が多い場合は、トークン使用量を考慮して以下を実施:

- 重要なファイル (実装ファイル、設定ファイル) を優先的にレビュー
- 自動生成ファイル、lock ファイル、バイナリファイルは除外

```bash
gh pr diff {pr_number}
```

または、特定ファイルのみ:

```bash
gh pr diff {pr_number} -- {file_path}
```

### 3. コードレビューの実施

次のカテゴリの観点でコードを評価する。差分だけで判断できないときは、関連ファイルを読む。

- バグ
- セキュリティ
- パフォーマンス
- 可読性
- ベストプラクティス
- テスト

PR のコードは、テストやビルドも含めて手元で実行しない。PR のコードは作者が書いたもので、実行するとユーザーの権限で任意の処理が動くため。動作を確かめたいときは、`gh pr checks` で CI の結果を見るか、コードを読んで、実害が起きる入力と手順を示す。`gh pr checks` が「no checks reported」で異常終了したときは、CI が設定されていないので、コードを読んで確かめる。言語やライブラリの挙動を確かめるために、PR のコードを読み込まない最小のコードを自分で書いて実行するのはよい。

利用者の操作 (画面の操作や、関数・API の呼び出し) で起きるバグを指摘するときは、再現手順を書く。レビューを依頼したユーザーも PR の作者も、指摘が本当に再現するかを自分で確かめられるようにするため。

各指摘には、作者に求める対応で次の重要度を付ける。作者は重要度を見て、マージを止めるか、この PR で直すか、後回しにするかを決めるため。境目で迷ったら低いほうにする。[must] が多いと、作者はどれが本当にマージを止める指摘かを見分けられなくなるため。

- **[must]**: 直さずにマージすると、利用者や運用に実害が出る。実害が起きる入力や手順を具体的に示せるものに限り、示せないものは起こりうるとしても [should] にする
  - 例: 通常の使い方で起きるバグ、外部から入力できる値で突ける脆弱性、データの破損、既存機能の破壊
- **[should]**: すぐに実害は出ないが、この PR で直さないと、後で直す手間が増える
  - 例: 今回の変更で使われなくなったコード、将来の変更で壊れやすい暗黙の前提、データ量が増えると問題になる計算量
- **[may]**: 直すかどうかを作者が決めてよい。今直さなくても、後で直す手間は変わらない
  - 例: より読みやすい書き方、周辺コードの慣習に揃える提案
- **[nit]**: 作者が対応しなくても、返信も不要
  - 例: 誤字、表記ゆれ、好みの範囲のスタイル

例は判断の目安で、上の基準のほうを優先する。例えば計算量の問題でも、今のデータ量で実害が出ると示せるなら [must] にする。

テストがないことを指摘するのは、リポジトリにテストがあり、動作を変えた処理に対応するテストが追加・更新されていない場合に限る。重要度は [should] にする。リポジトリにテストがない場合は、テストの仕組みを作ることが PR の範囲を超えるので指摘しない。

### 4. レビュー結果の作成

レビュー結果は、GitHub のレビューとして投稿できる形で作る。各指摘は該当する行へのインラインコメントにし、レビュー全体の本文には承認可否などの全体に関わる内容だけを書く。指摘を 1 件のコメントにまとめると長くなり、どの行の話かも読み手が探すことになるため。

投稿内容は、次の形式の Markdown ファイルとしてスクラッチパッド (なければ一時ディレクトリ) に書き出す。5 で、スクリプトがこのファイルから、レビュー作成 API に渡す JSON とプレビューを作る。表示した内容と投稿する内容を必ず一致させ、JSON のエスケープの誤りも避けるため。

````markdown
{レビュー全体の本文 (4.2)}

<!-- comment path=service.js line=42 -->
{インラインコメントの本文 (4.1)}

<!-- comment path=api.ts start_line=10 line=12 -->
{複数行に付けるインラインコメントの本文}
````

- 最初の `<!-- comment ... -->` 行より前が、レビュー全体の本文になる
- `<!-- comment ... -->` 行には、`キー=値` を空白で区切って 1 行で書く。値に空白は使えない
  - `path`: ファイルのパス
  - `line`: コメントを付ける行。範囲に付けるときは終了行
  - `start_line`: 範囲に付けるときの開始行
  - `side`: 削除された行に付けるときだけ `LEFT` を書く。省略すると `RIGHT` になる
- 行番号は、変更後のファイルの行番号で書く。`side=LEFT` のときだけ、変更前のファイルの行番号で書く
- インラインコメントを付けられるのは、差分のハンクに含まれる行 (追加・削除された行と、その前後の文脈行) だけ。差分の外の行を指定すると、API がレビュー全体を受け付けない

#### 4.1 インラインコメントの本文

````markdown
<sub>🤖 Claude <モデル名> によるレビュー</sub>

**No. 1 [must]** `user.profile` が null のとき TypeError になります。

ログイン前のユーザーでは `profile` が未設定のため、この行が実行時エラーになります。

```suggestion
const result = user?.profile?.email?.toLowerCase() ?? '';
```
````

- 1 行目に `<sub>🤖 Claude <モデル名> によるレビュー</sub>` を書き、空行を挟んで本文を続ける。投稿者はユーザーのアカウントとして表示されるので、内容を読む前に Claude が書いたものだと分かるようにするため。`<モデル名>` は 4.2 の見出しと同じにする
- 署名の後の段落の 1 行目に No. と重要度を付け、何が問題かを 1 文で書く
- No. は全指摘の通し番号にし、差分に現れる順 (`gh pr diff` の出力でのファイルの順、ファイルの中では `line` の順) に振る。GitHub の画面はこの順にコメントを並べ、範囲コメントも終了行 (`line`) の位置に表示するので、読み手が上から番号を追えるため
  - 差分の外への指摘 (4.2) は、インラインコメントの後に続けて番号を振る
- Markdown のコメントも No. の順に並べる。プレビューを GitHub の画面と同じ順に表示するため
- 2 段落目には、なぜ問題かを 1〜2 文で書く。1 行目で伝わるなら省く
- コメントは、問題のある行に付ける
- 修正が連続した行の置き換えで済むときは、`suggestion` ブロックで修正案を示す。GitHub の画面からそのまま適用できるため
  - `suggestion` はコメントを付けた範囲全体を置き換えるので、範囲は問題のある行を含めたうえで、置き換えが必要な最小の範囲まで広げる
  - 修正が離れた複数の箇所にまたがるときは `suggestion` を使わない。問題のある行にだけコメントを付け、修正案は `<details><summary>詳細</summary>` の中に通常のコードブロックで示す
- 再現手順は `<details><summary>再現手順</summary>` で折りたたむ
  - 次の順に書く: 操作または呼び出し例、期待する結果、実際に起きる結果
  - 手元の環境に固有のパスやコマンドは書かない。PR の作者の環境には存在しないため
- 置き換えで済まない修正案や、別案の比較のように長くなる説明は、`<details><summary>詳細</summary>` で折りたたむ
- 問題のある行が差分の外にあっても、原因が差分内の変更にあるときは、原因の行にインラインコメントを付け、影響を受ける箇所を `ファイル:行` で示す
- 原因と直し方が同じ指摘は、1 件のインラインコメントにまとめる。複数のファイルで同じ誤りを繰り返している PR で、同じ内容のコメントが並ばないようにするため
  - コメントは、影響が最も大きい箇所に付ける。影響に差がなければ、差分の中で最初に現れる箇所に付ける
  - 重要度は、まとめた箇所のうち最も高いものにする
  - 本文の最後に「同じ問題が次の箇所にもあります。」と書き、残りの箇所を `ファイル:行` で並べる
  - `suggestion` は、コメントを付けた箇所の分だけ書く
- 1 つの修正で複数の指摘が同時に直る場合も、1 件にまとめる。重要度は、まとめた指摘のうち最も高いものにする

#### 4.2 レビュー全体の本文

```markdown
## Claude <モデル名> によるレビュー

**承認可否**: ❌ 修正が必要

インラインコメント: [must] 2 件、[should] 1 件、[nit] 1 件

**全体所見**: No. 1 を直すと No. 3 の呼び出し方も変わるので、No. 1 から先に直すのがよいと考えます。

### 差分の外への指摘

- No. 5 [should] `config.js:120`
  - タイムアウトの既定値が、今回追加した呼び出しの想定より短い

<details>
<summary>良好な実装</summary>

- エラーハンドリングが適切に実装されている (error-handler.ts:15-30)

</details>
```

- 見出しは `## Claude <モデル名> によるレビュー` にする。人間のレビューと区別できるようにするため、依存関係更新 PR かどうかによらず必ず付ける。`<モデル名>` には現在の会話のシステムプロンプトに記載された Claude のモデル表示名 (例: `Opus 5`、`Sonnet 5`、`Haiku 4.5`) を入れ、1M context 版などのサフィックスがあれば併記する (例: `Opus 5 (1M context)`)
- **承認可否** は次のいずれかにする
  - ❌ 修正が必要 ([must] が 1 件以上)
  - ⚠️ 修正を推奨 ([should] が 1 件以上)
  - ✅ 承認可能
- インラインコメントの件数を重要度ごとに書く。0 件の重要度は省き、指摘が 1 件もなければ件数の行ごと書かない
- **全体所見** は、個々の指摘に書けない内容 (指摘どうしの関係、修正の順序、PR 全体の設計やテスト方針への懸念) があるときだけ 1〜2 文で書く。個々の指摘を言い直すだけになるなら書かない
- 差分の外への指摘は、インラインコメントを付けられず、原因も差分内にないものだけを書く。なければ節ごと省く
- 良好な実装は `<details>` で折りたたむ。なければ省く
- `<summary>` の後と `</details>` の前に空行を入れる。空行がないと GitHub が中の Markdown を描画しないため

### 5. 結果の提示と投稿

出力先をユーザーに尋ねず、レビュー結果は常にこのチャットに表示する。ユーザーは結果を見るまで PR に投稿するかを決められないため。

1. Markdown ファイルから、JSON とプレビューを生成する。スクリプトは、インラインコメントの行がすべて差分の中にあるかを検査し、Markdown ファイルの拡張子を `.json` に変えたパスに JSON を書き出して、対象行のコードと一緒にプレビューを出力する。差分の外の行があると、JSON を書き出さずに異常終了してその行を示すので、Markdown を直してから再実行する

   ```bash
   python3 ~/.claude/skills/review-pr/scripts/preview_review.py {owner}/{repo} {pr_number} {Markdown ファイルのパス}
   ```

2. スクリプトの出力の先頭に「書きかけのレビュー (PENDING) があります」という警告が出たら、プレビューと一緒にユーザーに伝える。ユーザーが GitHub の画面で書きかけのレビューを送信するか破棄するまで、投稿は失敗するため
3. スクリプトの出力を、そのまま `markdown` のコードブロックで囲んで提示する。出力の中のコードブロックで途中で閉じないよう、外側は 4 つのバッククォートで囲む
4. 提示したターンでは、投稿するかを尋ねない。PR への投稿は、ユーザーから投稿の指示を受けたときだけ行う

投稿の指示を受けたら、次のコマンドで送信前の下書きとしてレビューを作成する。指示と一緒に内容の修正を求められた場合は、Markdown を直してプレビューを再表示し、承認を得てから投稿する。

```bash
gh api --method POST repos/{owner}/{repo}/pulls/{pr_number}/reviews --input {手順 1 で書き出された JSON ファイルのパス}
```

- JSON には `event` を入れないので、レビューは送信前の下書き (PENDING) になる。ユーザーが GitHub の画面で内容を確かめてから、Approve / Request changes を選んで自分で送信できるようにするため
- `--method POST` は省略・短縮せず、この形で書く。ユーザーの権限設定はこの書き方に一致したときに確認を出すため
- 投稿後は PR の URL を示し、GitHub の「Files changed」画面で内容を確かめてから、Approve / Request changes / Comment のいずれかを選んで送信するよう伝える

## エラーハンドリング

- 差分が大きすぎる場合は、ユーザーに確認して範囲を絞る
