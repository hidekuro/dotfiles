# PR コードレビュー実施

## ワークフロー

### 1. PR 番号の取得

現在のブランチから PR 番号を自動取得:

```bash
gh pr view --json number --jq '.number'
```

PR が存在しない場合は、ユーザーに PR 番号または PR URL の入力を求めます。

### 2. PR 情報の取得

#### 2.1 PR 本文と基本情報の取得

```bash
gh pr view {pr_number} --json title,body,author,baseRefName,headRefName,additions,deletions,labels
```

#### 2.2 依存関係更新 PR の判定

取得した情報から、PR が renovate / dependabot による依存関係更新かを判定する。次のいずれかに該当する場合、後述の「依存関係更新 PR のレビュー」フローに分岐する:

- `author.login` が `renovate[bot]`、`dependabot[bot]`、`renovate-bot` などの bot アカウント
- `labels[].name` に `dependencies`、`renovate`、`dependabot` などが含まれる

判定が真の場合は、通常のコードレビュー観点ではなく、依存パッケージ更新の安全性評価を行う。専用フローの詳細は `references/dependency-update-review.md` を読んで実施する。

#### 2.3 変更ファイル一覧の取得

```bash
gh pr diff {pr_number} --name-only
```

#### 2.4 コード差分の取得

ファイル数が多い場合は、トークン使用量を考慮して以下を実施:

- 重要なファイル (実装ファイル、設定ファイル) を優先的にレビュー
- 自動生成ファイル、lock ファイル、バイナリファイルは除外

```bash
gh pr diff {pr_number}
```

または、特定ファイルのみ:

```bash
gh pr diff {pr_number} -- {file_path}
```

### 3. コードレビューの実施

4.2 のカテゴリの観点でコードを評価する。差分だけで判断できないときは、関連ファイルを読む。

### 4. レビュー結果の報告

レビュー結果を PR にコメントとして投稿するときは、本文の冒頭に `## Claude <モデル名> によるレビュー` の見出しを置く。人間のレビューと区別できるようにするため、依存関係更新 PR かどうかによらず必ず付ける。`<モデル名>` には現在の会話のシステムプロンプトに記載された Claude のモデル表示名 (例: `Opus 5`、`Sonnet 5`、`Haiku 4.5`) を入れ、1M context 版などのサフィックスがあれば併記する (例: `Opus 5 (1M context)`)。

#### 4.1 PR 概要

まず、PR の概要を簡潔に要約:

```markdown
## PR 概要

- **タイトル**: [PR タイトル]
- **作成者**: [作成者]
- **変更規模**: +X 行 / -Y 行
- **変更ファイル数**: Z ファイル
- **目的**: [PR 本文から読み取った変更の目的]
```

#### 4.2 レビュー指摘事項

各指摘事項を表形式で提示:

| No. | ファイル:行 | カテゴリ | 重要度 | 指摘内容 |
|---|---|---|---|---|
| 1 | service.js:42 | バグ | [must] | null チェックが不足しており、実行時エラーが発生する可能性 |
| 2 | api.ts:10 | セキュリティ | [must] | ユーザー入力が直接 SQL に埋め込まれており、SQL injection の脆弱性 |
| 3 | utils.js:55 | パフォーマンス | [should] | ループ内で不要な計算を繰り返しており、計算量が O(n²) |
| 4 | component.tsx:20 | 可読性 | [nit] | 変数名 `x` は意味が不明確。より具体的な名前が望ましい |

**カテゴリ**:
- バグ
- セキュリティ
- パフォーマンス
- 可読性
- ベストプラクティス
- テスト

**重要度**:
- **[must]**: 必ず修正が必要。バグや脆弱性など、マージ前に対応すべき問題
- **[should]**: 修正を強く推奨。動作するが、保守性・品質の観点から改善すべき
- **[may]**: 任意の改善提案。対応するとより良くなる可能性がある
- **[nit]**: ごく軽微な指摘。タイポ、コメント、スタイルなど

#### 4.3 詳細な分析

重要度が `[must]` または `[should]` の指摘については、詳細な分析を追記:

````markdown
### 詳細分析

#### 指摘 No. 1: service.js:42 - null チェック不足

**問題箇所**:

```javascript
const result = user.profile.email.toLowerCase();
```

**問題点**:
`user.profile` または `user.profile.email` が null/undefined の場合、TypeError が発生する。

**推奨修正**:

```javascript
const result = user?.profile?.email?.toLowerCase() ?? '';
```

または、事前にバリデーションを実施:

```javascript
if (!user?.profile?.email) {
  throw new Error('Email is required');
}
const result = user.profile.email.toLowerCase();
```
````

#### 4.4 肯定的な評価

良い実装についても言及する:

```markdown
## 良好な実装

- エラーハンドリングが適切に実装されている (error-handler.ts:15-30)
- テストカバレッジが高く、エッジケースもカバーされている
- 命名が明確で、コードの意図が理解しやすい
```

#### 4.5 総合評価

最後に、総合的な評価とアクションを提示:

```markdown
## 総合評価

**承認可否**: ❌ 修正が必要 / ⚠️ 修正を推奨 / ✅ 承認可能

**要約**:

- [must]: X 件
- [should]: Y 件
- [may]: Z 件
- [nit]: W 件

**推奨アクション**:

1. [must] の問題 (No. 1, No. 2) を修正
2. [should] の問題 (No. 3) の対応を検討
3. [may] / [nit] は任意だが、対応するとコード品質が向上
```

#### 4.6 出力先の選択

レビュー結果を提示する前に、ユーザーに出力方法を確認する。

> "レビューが完了しました。次のいずれの方法で提示しますか？
> 1. このチャットにマークダウンコードブロックで表示 (ユーザーがコピーして使用)
> 2. PR に直接コメントとして投稿"

選択に応じて以下を実行する:

- **1 を選択**: レポート全体を `markdown` のコードブロックで囲んで提示し、ユーザーがそのままコピー&ペーストで PR コメントに転記できる形にする。レポート内のコードブロックで途中で閉じないよう、外側は 4 つのバッククォートで囲む。
- **2 を選択**: 投稿する本文を提示して承認を得てから、`gh pr comment` で PR に投稿する。投稿後、コメントの URL を提示する。

```bash
gh pr comment {pr_number} --body-file - <<'EOF'
## Claude <モデル名> によるレビュー

...
EOF
```

## エラーハンドリング

- 差分が大きすぎる場合は、ユーザーに確認して範囲を絞る
