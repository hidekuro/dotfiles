# 今日の作業の切り上げ

翌日の自分 (別セッションの AI) が、この会話を読まずに作業を再開できる状態にする。会話は要約や再開の過程で詳細が落ちるので、再開に必要な情報は memory に書き出す。

## 手順

### 1. 現状を整理する

この会話を振り返り、次を洗い出す。

- 待っている返事
  - 人間に出して答えを待っている質問と、承認待ちの操作
  - 切り上げの直前が質問で終わっていると、翌日の AI は質問したこと自体を忘れて先に進むので、最初に拾う
- 確定したこと
  - ユーザーと合意した決定事項、完了した作業
- 未着手・途中のこと
  - 残っている作業と、途中の作業がどこまで進んでいるか
- 試して駄目だったこと
  - 採らなかった方法とその理由、つまずきやすい点
- 次の具体アクション
  - 再開したら最初にやること 1 つ
  - 再開後に使うスキル (conductor、create-pr、handle-review-comments など) があればそれも
- 関連する場所
  - ブランチ名、PR / issue の URL、作業中のファイル、仕様ドラフトなどのドキュメント
  - 参照先ごとに、そこで読むべき箇所 (節や行の範囲) を添える。パスだけだと再開した AI が全文を読むことになるため
- 検査の状態
  - lint・テストを最後に回した結果 (通った / 失敗 / 回していない)。再開後に最初に回すべきかを判断できるようにするため

git 管理下で作業していた場合は `git status --short --branch` と `git rev-parse HEAD` を実行し、ブランチ名・HEAD の値・未コミットの変更があればそのことを記録する。再開時に HEAD が進んでいれば、memory の記述が古いと分かるため。コミットやプッシュはこのスキルの範囲外なので、指示がない限り実行しない。

### 2. memory に保存する

`project` タイプの memory として保存する。

- 未回答の質問と承認待ちの操作は、本文の先頭に置く
- 同じ作業についての memory が既にあれば、新しく作らずにそのファイルを更新する。古くなった記述は消す
- 日付は「今日」「明日」と書かず、絶対日付で書く (例: 2026-10-02 時点)
- 確認した事実と推測を分けて書く。確認していない項目は「未確認」と明記する
- PR・issue・`tasks.md` などにすでに書いてある内容は複製せず、URL やパスで示す。複製すると、元の記述が更新されたときに memory だけが古いまま残るため
- 書く前に、API キー・トークン・個人情報が本文に入っていないかを見て伏せる。memory に残ると、以後のセッションの文脈に毎回載るため
- 書いたパスと URL が存在するかを確かめる。消えたファイルへのパスは再開時の空振りになるため
- 書き終えたら、文脈ゼロの人がこの memory だけを読んで次の一手を実行できるかで読み返す。「リファクタの続き」のような文は不可で、ファイルパス・手本になる既存コード・次の 1 手が書けていることを確かめる。翌日の AI が再開に失敗するのは、たいてい次アクションの粒度が粗いときのため

### 3. 次セッションでの指示例を提示する

翌日そのまま貼れる指示を、コードブロックで 1 つ提示する。CLAUDE.md の再開時の規則 (あらすじを返す) が働くよう、「〇〇の作業を再開します」で始める。指揮モードで進めていた作業なら「〇〇の作業を指揮モードで再開します」にする。再開した AI はどのスキルで進めていたかを知らないため。

```text
<作業名> の作業を再開します。<次の具体アクション> から始めたいです。
```

```text
<作業名> の作業を指揮モードで再開します。<次の具体アクション> から始めたいです。
```

## 報告の形

次の 3 つを短く書く。報告のみにして、質問や「他に残すことはありますか」のような確認を付けない。

1. 保存した memory のファイル名と、確定したこと・未着手のことの要約 (各 1〜3 行)。未回答の質問があればそれも
2. 未コミットの変更がある場合はその旨とブランチ名
3. 次セッションでの指示例
