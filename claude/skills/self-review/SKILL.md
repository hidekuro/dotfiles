# セルフレビュー

直前に自分が実装した変更を、実装の経緯を知らないサブエージェントにレビューさせる。実装者のコンテキストには「こう書いた理由」がそのまま残っていて自分の判断を追認しやすいため、レビューは新規のサブエージェントに任せる。

## 手順

### 1. レビュー対象を決める

原則として未コミットの変更全体を対象にする。

```bash
git status --porcelain
```

```bash
git diff HEAD
```

- `git diff HEAD` は未追跡ファイルを含まない。`git status --porcelain` で `??` が付いたパスは差分に一切現れないので、ファイルパスの一覧として別途レビュー役に渡し、本文を直接読ませる。新規に追加したファイルがまるごとレビューされないのは、このスキルで最も起きやすい失敗
- 未コミットの変更がなければ、デフォルトブランチとの差分 (`git diff origin/main...HEAD`) を対象にする。ベースブランチ名はリポジトリごとに違うので `git remote show origin` や `git branch -r` で確かめて埋める。`origin/HEAD` は設定されていないリポジトリがあり、そのまま書くと失敗する。判別できなければユーザーに確認する
- git 管理外のファイルを編集したときも、そのパスを対象に加える
- 差分が大きいときは、自動生成ファイル・lock ファイル・ビルド成果物を対象から除く
- 書式整形や typo 修正だけの軽微な変更でも、指示されたなら起動する。その場合は観点を絞って短く済ませる

### 2. レビュー役を起動する

Agent ツールで 1 回だけ起動する。指摘ごとの検証エージェントや観点別のファンアウトはこのスキルの範囲外。

- `subagent_type`: `general-purpose`
- `model`: セッションで使える最も判断精度の高いモデルを明示する。Agent ツールの `model` の選択肢に `fable` があれば `fable`、なければ `opus`。レビューは実装よりも高い判断精度を要するので、セッションのモデルが何であれ指定する
- `fork` は使わない。実装時の判断や前提をそのまま引き継ぐため、独立した視点にならない

出力先は、このセッションのスクラッチパッドディレクトリ配下の `self-review-<対象を表す語>.md` を絶対パスで指定する (例: `self-review-auth-refactor.md`)。作業対象のリポジトリ内には作らない。同名のファイルが既にあれば `-2`、`-3` と連番を付けて前回の結果を残す。修正前後を見比べられるようにするため。

依頼文は「依頼文の雛形」を埋めて渡す。渡し方で守ること:

- 実装の意図・採用理由・検討の経緯は渡さない。レビュー役がそれらを読むと、実装者の判断を追認する方向へ引きずられるため
- 「〇〇は意図的なので指摘しない」「〇〇は軽微な扱いで」のように、指摘を先回りして封じる文を書かない。レビュー役に挙げさせ、実装者が見解で退ける
- 評価観点は、共通の観点に、対象の種類に当たる観点を足して渡す。当たらない種類の観点は消す。コードの観点で AI への指示文を見ても、理由のない命令や効いていない記述のような指示文に固有の不備は見つからないため。雛形にない種類の対象 (設計文書や下書きなど) は、その対象に固有の不備が何かを考えて観点を書く

### 3. 結果を読み、判断できなかったものを処理する

保存されたファイルを読む。レビュー役の最終応答の要約だけで判断しない。

レビュー結果の「判断できなかったもの」は、レビュー役が確かめなかった範囲の一覧で、読み手は実装者。そのまま人間に見せても、人間はそれを受けて何をすべきかが分からないので、報告の前に実装者が 1 件ずつ処理する。

- 数回のツール呼び出しで確かめられるものは確かめ、結果を指摘の一覧の行にする
- 確かめられないものは、「未確認のまま進めてよいか」を問う判断事項として指摘の一覧の行にする。ただし、手順やコマンドの動作のように試せば確かめられるものは、判断事項にせず試す段取り (何を対象に、何を見て確かめるか) を示す。共有前に試すのが前提なので、確かめずに進めるかは判断事項にならないため
- 「要件の範囲外として指摘しなかった挙動」は、要件に足すべきかを実装者が判断し、足すべきものは指摘の一覧の行にする

### 4. 報告する

同じターンで次の 5 つを提示する。人間は作業の文脈を覚えていない前提で、この報告だけ読んで答えられるように書く。

1. 何の作業のレビューかを 1 行と、レビュー結果ファイルの絶対パス
2. 凡例を 1 行 (レビュー役は経緯を知らない別の AI、実装者はこの報告を書いている AI)
3. 指摘の一覧 (No. / 出どころ / ファイル:行 / 重要度 / 指摘の要約)
   - 出どころは「レビュー役の指摘」「レビュー役が判断できなかった点」「実装者」のいずれか
   - レビュー役の指摘に加えて、手順 3 で処理した点と、実装者が自分で気づいた問題も行にする
4. 各指摘への見解 (No. で指す)
5. 判断を仰ぎたい点
   - 見解で「判断を仰ぎたい」とした指摘を集め、何を決めてほしいかと、選ぶと何が変わるかを添える
   - なければ「判断を仰ぐ点はなし」と書く。人間が見る場所をここ 1 か所にし、保留中のものがあるかもここで分かるようにするため

レビュー役の記述と実装者の判断は、置く場所で見分けられるようにする。どちらの判断かが混ざると、人間は独立したレビュー役の判断がどれかを見分けられなくなるため。

- 実装者の判断はすべて見解に書く。指摘の要約には、出どころが実装者の行を除き、レビュー役の記述の要約だけを書く
- 人間向けの報告に「判断できなかったもの」という項目を置かない

見解の書き方:

- 指摘ごとに「対応する」「対応しない」「判断を仰ぎたい」のいずれかを明示し、理由を 1〜2 文添える
- レビュー結果を無条件には受け入れない。レビュー役も誤るので、事実として誤っている指摘・このリポジトリでは当てはまらない指摘は根拠を示して否定する
- 修正の実施はこのスキルの範囲外。見解の提示までで一度止め、その場で着手の許可を求めない
- [must] と [should] の指摘は、ユーザーの判断が要るものも含めてすべて解決してからコミットを提案する。解決とは、直したか、根拠を示して「対応しない」としたことにユーザーが同意した状態。「コミットして」と言われた時点で未解決の [must] / [should] が残っていたら、コミットの案を出す前にそのことを伝え、先に解決する

### 5. 修正の後に再レビューするとき

再レビューを指示されたとき、または指揮モードのように指示なしに起動してよい場面で、[must] か [should] の指摘に対応して成果物が変わったときに、新しいレビュー役を起動して再レビューさせる。前回のレビュー役に頼むと、自分の指摘が直ったかだけを見る方向に偏るため。指示なしに起動してよい場面でも、それ以外の指摘への対応では再レビューしない。回数の歯止めのため。

再レビューの依頼文には、前回のレビュー結果のファイルのパスを添え、次の 2 つを分けて頼む。実装者の判断 (「対応しない」とした指摘とその理由) と作業の経緯は渡さない。直っていない指摘や退けた指摘がもう一度挙がれば、実装者の判断を見直すきっかけになるため。

- 前回の指摘 1 件ずつについて、今の成果物で解消しているかを「解消 / 未解消」と根拠の行で判定し、「前回の指摘の状態」の表として書く
- それとは別に、成果物全体を新しく見てレビューする。前回の指摘に引きずられず、前回が見落とした点を探す

## 依頼文の雛形

```markdown
次の変更をレビューし、結果を指定のファイルに書き出してください。

## 対象

- リポジトリ: <リポジトリの絶対パス>
- 差分の取得: `git diff HEAD` (または対象を絞ったコマンド)
- 未追跡の対象ファイル: <パスの一覧。なければ「なし」>

## この変更が満たすべき要件

<ユーザーからの元の依頼内容をそのまま>

## 前提

- リポジトリの規約は自分で確認してください (CLAUDE.md, README, lint / formatter の設定ファイル)
- 問題がなければ「指摘なし」と書いてください。指摘を捻り出す必要はありません
- 作業ツリー・インデックス・HEAD を変更しないでください (指定の出力ファイルへの書き出しを除き、ファイルの編集、`git add`、`git commit`、`git stash` をしない)
- サブエージェントを起動しないでください

## 評価観点

共通:

- 要件の充足漏れ・過剰実装
- 過剰適合 (要件のきっかけになった 1 件の事例だけに当てはまる対応になっていて、同じ種類の別の事例には効かない)

対象がコードのとき:

- バグ・潜在的な問題 / セキュリティ / パフォーマンス / 可読性・保守性 / テスト
- コメント (コードから読み取れる内容の復唱・作業経緯の記述・冗長さ・周辺の慣習との不一致・コードの動作との食い違い)

対象が AI への指示文 (SKILL.md とスキルが参照するファイル、CLAUDE.md、AGENTS.md) のとき:

- 指示に理由が書かれているか。大文字の ALWAYS / NEVER や硬い構造で縛って、理由の説明に代えていないか
- 効いていない記述や重複がないか
- SKILL.md が長くなりすぎていないか。詳細を参照ファイルに分けているなら、それを読む条件が示されているか
- description が、そのスキルを使う条件を具体に書いているか

## 指摘しないもの

- この変更が入れたものではない既存の問題
- linter や formatter が拾うもの
- lint ignore のコメントなどで、コード側が意図的に抑制しているもの
- 反証できたもの。不具合と思う箇所は、引き金になる入力や順序が到達可能か、呼び出し側や既存のガードで防がれていないかを確かめてください。反証できたら指摘に入れず、反証も確認もできなければ「判断できなかったもの」に書いてください

## 重要度

- [must]: マージ前に必ず修正が必要
- [should]: 修正を強く推奨
- [may]: 任意の改善提案
- [nit]: タイポ・スタイル等の軽微な指摘

## 出力

下記の構成で <出力先の絶対パス> に書き出してください。最終応答にはファイルの絶対パスと重要度別の件数だけを返し、本文は返さないでください。指摘の項番は `#` + 数字ではなく `No. 1` と書いてください。

# セルフレビュー結果: <対象の要約>

## 概要

変更の内容を 2〜3 行で要約する。

## 指摘事項

| No. | ファイル:行 | カテゴリ | 重要度 | 指摘内容 |
|---|---|---|---|---|

## 詳細

[must] と [should] の指摘について、問題箇所・問題点・推奨修正を書く。

## 判断できなかったもの

確かめられずに指摘しなかった挙動を、1 行ずつ理由を添えて書く。なければ「なし」と書く。
要件の範囲外と判断して指摘しなかった挙動 (要件に書かれていない入力や条件) も、分けて 1 行ずつ書く。なければ「なし」と書く。

## 良好な点

## 総評

重要度別の件数と、全体としての評価。
```
