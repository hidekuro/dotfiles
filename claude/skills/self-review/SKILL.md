# セルフレビュー

直前に自分が実装した変更を、実装の経緯を知らないサブエージェントにレビューさせる。実装者のコンテキストには「こう書いた理由」がそのまま残っていて自分の判断を追認しやすいため、レビューは新規のサブエージェントに任せる。

## ワークフロー

### 1. レビュー対象を確定する

原則として未コミットの変更全体を対象にする。

```bash
git status --porcelain
```

```bash
git diff HEAD
```

`git diff HEAD` は未追跡ファイルを含まない。`git status --porcelain` で `??` が付いたパスは差分に一切現れないため、ファイルパスの一覧として別途サブエージェントに渡し、本文を直接読ませる。新規追加したファイルがまるごとレビューされないのは、このスキルで最も起きやすい失敗。

未コミットの変更がない場合は、デフォルトブランチとの差分を対象にする。

```bash
git diff origin/main...HEAD
```

ベースブランチ名はリポジトリごとに異なるので `git remote show origin` や `git branch -r` で確認して埋める。`origin/HEAD` は設定されていないリポジトリがあり、そのまま書くと失敗する。判別できない場合はユーザーに確認する。

git 管理外のファイルを編集した場合も、そのパスを対象に加える。

### 2. サブエージェントを起動する

Agent tool で 1 回だけ起動する。指摘ごとの検証エージェントや観点別のファンアウトはこのスキルの範囲外。

- `subagent_type`: `general-purpose`
- `model`: `opus` — レビューは実装よりも高い判断精度を要するので、セッションのモデルが何であれ明示的に指定する
- `fork` は使わない — 実装時の判断や前提をそのまま引き継ぐため、独立した視点にならない

出力先は、このセッションのスクラッチパッドディレクトリ配下の `self-review-<対象を表す語>.md` を絶対パスで指定する (例: `self-review-auth-refactor.md`)。同名のファイルが既にあれば `-2`, `-3` と連番を付けて前回の結果を残す。修正前後を見比べられるようにするため。

雛形の評価観点は、共通の観点に、対象の種類に当たる観点を足して渡す。当たらない種類の観点は消す。コードの観点で AI への指示文を見ても、理由のない命令や効いていない記述のような指示文に固有の不備は見つからないため。雛形にない種類の対象 (設計文書や下書きなど) は、その対象に固有の不備が何かを考えて観点を書く。

プロンプトは次の雛形を埋めて渡す。実装の意図・採用理由・検討の経緯は渡さない。レビュアーがそれらを読むと、実装者の判断を追認する方向へ引きずられるため。

```markdown
次の変更をレビューし、結果を指定のファイルに書き出してください。

## 対象

- リポジトリ: <リポジトリの絶対パス>
- 差分の取得: `git diff HEAD` (または対象を絞ったコマンド)
- 未追跡の対象ファイル: <パスの一覧。なければ「なし」>

## この変更が満たすべき要件

<ユーザーからの元の依頼内容をそのまま>

## 前提

- リポジトリの規約は自分で確認してください (CLAUDE.md, README, lint / formatter の設定ファイル)
- 問題がなければ「指摘なし」と書いてください。指摘を捻り出す必要はありません
- 作業ツリー・インデックス・HEAD を変更しないでください (指定の出力ファイルへの書き出しを除き、ファイルの編集、`git add`、`git commit`、`git stash` をしない)
- サブエージェントを起動しないでください

## 評価観点

共通:

- 要件の充足漏れ・過剰実装
- 過剰適合 (要件のきっかけになった 1 件の事例だけに当てはまる対応になっていて、同じ種類の別の事例には効かない)

対象がコードのとき:

- バグ・潜在的な問題 / セキュリティ / パフォーマンス / 可読性・保守性 / テスト
- コメント (コードから読み取れる内容の復唱・作業経緯の記述・冗長さ・周辺の慣習との不一致・コードの動作との食い違い)

対象が AI への指示文 (SKILL.md とスキルが参照するファイル、CLAUDE.md、AGENTS.md) のとき:

- 指示に理由が書かれているか。大文字の ALWAYS / NEVER や硬い構造で縛って、理由の説明に代えていないか
- 効いていない記述や重複がないか
- SKILL.md が長くなりすぎていないか。詳細を参照ファイルに分けているなら、それを読む条件が示されているか
- description が、そのスキルを使う条件を具体に書いているか

## 重要度

- [must]: マージ前に必ず修正が必要
- [should]: 修正を強く推奨
- [may]: 任意の改善提案
- [nit]: タイポ・スタイル等の軽微な指摘

## 出力

下記の構成で <出力先の絶対パス> に書き出してください。最終応答にはファイルの絶対パスと重要度別の件数だけを返し、本文は返さないでください。指摘の項番は `#` + 数字ではなく `No. 1` と書いてください。

# セルフレビュー結果: <対象の要約>

## 概要

変更の内容を 2〜3 行で要約する。

## 指摘事項

| No. | ファイル:行 | カテゴリ | 重要度 | 指摘内容 |
|---|---|---|---|---|

## 詳細

[must] と [should] の指摘について、問題箇所・問題点・推奨修正を書く。

## 判断できなかったもの

確かめられずに指摘しなかった挙動を、1 行ずつ理由を添えて書く。なければ「なし」と書く。

## 良好な点

## 総評

重要度別の件数と、全体としての評価。
```

### 3. レビュー結果を読む

保存されたファイルを読む。サブエージェントの最終応答の要約だけで判断しない。

### 4. 判断できなかったものを処理する

レビュー結果の「判断できなかったもの」は、レビュー役が確かめなかった範囲の一覧で、読み手は実装者。そのまま人間に見せても、人間はそれを受けて何をすべきかが分からないので、報告の前に実装者が 1 件ずつ処理する。

- 数回のツール呼び出しで確かめられるものは確かめ、結果を指摘の一覧の行にする
- 確かめられないものは、「未確認のまま進めてよいか」を問う判断事項として指摘の一覧の行にする

### 5. 報告する

同じターンで次の 5 つを提示する。人間は作業の文脈を覚えていない前提で、この報告だけ読んで答えられるように書く。

1. 何の作業のレビューかを 1 行と、レビュー結果ファイルの絶対パス
2. 凡例を 1 行 (レビュー役は経緯を知らない別の AI、実装者はこの報告を書いている AI)
3. 指摘の一覧 — No. / 出どころ / ファイル:行 / 重要度 / 指摘の要約
   - 出どころは「レビュー役の指摘」「レビュー役が判断できなかった点」「実装者」のいずれか
   - レビュー役の指摘に加えて、手順 4 で処理した点と、実装者が自分で気づいた問題も行にする
4. 各指摘への見解 (No. で指す)
5. 判断を仰ぎたい点
   - 見解で「判断を仰ぎたい」とした指摘を集め、何を決めてほしいかと、選ぶと何が変わるかを添える
   - なければ「判断を仰ぐ点はなし」と書く。人間が見る場所をここ 1 か所にし、保留中のものがあるかもここで分かるようにするため

レビュー役の記述と実装者の判断は、置く場所で見分けられるようにする。どちらの判断かが混ざると、人間は独立したレビュー役の判断がどれかを見分けられなくなるため。

- 実装者の判断はすべて見解に書く。指摘の要約には、出どころが実装者の行を除き、レビュー役の記述の要約だけを書く
- 人間向けの報告に「判断できなかったもの」という項目を置かない

見解の書き方:

- 指摘ごとに「対応する」「対応しない」「判断を仰ぎたい」のいずれかを明示し、理由を 1〜2 文添える
- レビュー結果を無条件には受け入れない。サブエージェントも誤るので、事実として誤っている指摘・このリポジトリでは当てはまらない指摘は根拠を示して否定する
- 修正の実施はこのスキルの範囲外。見解の提示までで一度止め、その場で着手の許可を求めない

## 注意事項

- 軽微な変更 (書式整形・typo 修正のみ) でも、指示されたなら起動する。その場合は観点を絞って短く済ませる
- 差分が大きい場合は、自動生成ファイル・lock ファイル・ビルド成果物を対象から除く
- レビュー結果ファイルはスクラッチパッドに置く。作業対象のリポジトリ内には作らない
