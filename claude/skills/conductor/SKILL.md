# 指揮モード

指揮役 (このセッション) と、作業役・レビュー役 (サブエージェント) に仕事を分ける。目的は次の 2 つ。

- 上位モデルの利用量を、判断が要る場面だけに使う
- 作業の細かいログを指揮役のコンテキストに入れず、長い作業でも指揮役が全体を見失わないようにする

指揮役が Opus のときは 1 つ目の目的は成り立たないが、2 つ目の目的のために同じ手順で進める。

## 役割

指揮役 (このセッション) が受け持つこと:

- ゴールと完了条件を人間と合わせる
- 作業をタスクに分け、作業役に依頼する
- 設計の判断と評価 (候補の比較、既存コードの構造の読み解き、方針の選択)
- 作業役とレビュー役の報告を検査し、採るかを決める
- 承認が要る操作 (issue / PR への書き込み、コミット、push) と、人間への報告

作業役 (サブエージェント) に任せること:

- 結論が出ている内容の反映 (文書の修正、仕様が決まった実装)
- 手順が決まっている確認 (テスト・lint の実行、決まったクエリの再実行)
- 範囲を狭く切った調査

レビュー役 (サブエージェント) には、作業役の成果を、作業の経緯を知らない立場で見てもらう。

作業の途中で設計の判断が要る点に当たったら、作業役は自分で決めずに報告に書いて返す。判断まで作業役に任せると、指揮役を上位モデルで動かしている意味がなくなるため。

## 手順

### 1. 指揮役のモデルとゴールを合わせる

起動したら、作業に入る前に指揮役のモデルとゴールを合わせる。このターンは質問だけにして止める。

まず今のモデル名を 1 行で示し、このまま指揮役を続けるか、`/model` で切り替えてから続けるかを尋ねる。モデルはスキルからは切り替えられず、上位モデルの利用上限の残りや作業の難しさを知っているのも人間なので、人間に決めてもらう。作業役とレビュー役は、指揮役のモデルにかかわらず Opus にする。

あわせてゴールを確認する。先に `ls tmp` で、今回の作業に当たる `tmp/<作業名>/tasks.md` がすでにあるかを確かめる。

- 今回の作業の `tasks.md` がすでにあるとき (別のセッションで再開したとき)
  - それを読み、ゴール・完了条件・残りのタスクを再提示し、認識が合っているかの確認を求める。これが再開時のあらすじを兼ねる
- 作業の指示がまだないとき (「指揮モードで作業します」とだけ言われたとき)
  - ゴールと完了条件を尋ねる
- 作業の指示がすでにあるとき (同じメッセージで指示されたときと、指示の後に「指揮モードで進めて」と言われたときの両方)
  - 指示から読み取ったゴール・完了条件・タスクの分け方を再提示し、認識が合っているかの確認を求める

新しく始めるときは、作業名 (`tmp/<作業名>/` に使う短い英数字の名前) もゴールと一緒に示す。

完了条件は「何がどうなっていれば終わりか」を、出力ファイルや確認の方法で書く。完了条件が曖昧なまま始めると、指揮役が作業役の成果を採るかどうかを判断できないため。

### 2. 作業場所を用意する

成果物と作業記録は、作業ディレクトリ直下の `tmp/` に置く。中身が `*` の 1 行だけの `tmp/.gitignore` を置き、`.gitignore` 自身を含めて `tmp/` の中身をすべて git に無視させる。リポジトリの `.gitignore` を書き換えずに済むため。

作る前に、今の状態を次のコマンドで 1 つずつ確かめる。

```bash
ls -a tmp
```

```bash
git rev-parse --is-inside-work-tree
```

```bash
git ls-files tmp
```

```bash
git check-ignore tmp/<作業名>/tasks.md
```

結果に応じて次のようにする。既存のファイルは書き換えない。

- `tmp/` がない
  - 作って `tmp/.gitignore` を置く
- git が追跡しているファイルが `tmp/` にある
  - 追跡中のファイルと作業記録が混ざるので、手を付けずに人間に確認する
- `tmp/` の中身がすでに git に無視されている (`tmp/.gitignore` やリポジトリの `.gitignore` による)
  - そのまま使う
- `tmp/` の中身が無視されていない
  - `tmp/.gitignore` がなければ置く
  - `tmp/.gitignore` があるのに無視されていなければ、書き換えずに人間に確認する

`tmp/.gitignore` を置いたら、`git check-ignore` をもう一度実行して無視されたことを確かめる。

`git rev-parse --is-inside-work-tree` が失敗したら作業ディレクトリは git 管理外なので、残りの `git` の確認は飛ばし、`tmp/` と `tmp/.gitignore` がなければ作る。

作業ごとに `tmp/<作業名>/` を作り、そこに `tasks.md` を置く。コンテキストが要約されても、指揮役がゴールと進捗をこのファイルから取り戻し、次のタスクを自分で選べるようにするため。

- タスクを依頼したとき・終えたとき・判断したときに、その場で `tasks.md` を更新する
- 作業役は Agent ツールの `description` に短い名前 (例: `docs-fix`) を付けて起動し、タスクの行にはその名前と、起動結果が返す agentId を書く。SendMessage の宛先になるのは agentId だけで、`description` の名前は ListAgents に出ないため。agentId は人間に見せない値なので、`tasks.md` 以外 (人間への報告など) には書かない。別のセッションで再開したときは、agentId が使えるとは限らないので作業役を新しく起動する
- 人間への報告には毎回 `tasks.md` の絶対パスを書く。要約の後はまずこのファイルを読み直して続きを決める

```markdown
# <作業名>

conductor スキル (指揮モード) で進めている。要約の後や別のセッションで読み直したときは、スキルを読み込み直してから続ける。

## ゴール

## 完了条件

## タスク

- [ ] 1. <タスク> (担当: 指揮役 / 作業役「<名前>」 <agentId>)

## 判断の記録

- <何を決めたか>。理由: <理由>
```

### 3. 作業役に依頼する

Agent ツールで起動する。

- `subagent_type` は `general-purpose`
- `model` は `opus` を明示する。省略すると、既定では指揮役と同じモデルで動き、節約にならないため
- `fork` は使わない。`fork` は `model` を指定しても指揮役と同じモデルで動くため
- 1 タスクに作業役 1 体。同じタスクの手直しは新しく起動せず、SendMessage で同じ作業役に頼む。新しい作業役は入力を読み直すので、その分の利用量がかかるため
- 並列に起動するのは、互いの出力に依存せず、同じファイルを編集しないタスクだけにする

入力と出力のファイルを明示できないタスクは、依頼する前に分け直す。範囲が曖昧だと作業役が広く読み回り、利用量も結果のぶれも大きくなるため。100 ファイルを超えるような調査は範囲を狭く切り、複数回に分けて依頼する。

依頼文は次の雛形を埋める。

```markdown
次の作業をしてください。

## 目的

<このタスクが全体のゴールのどこを担うかを 1〜2 文で>

## 入力

- <読むファイルの絶対パス、URL、issue 番号>

## 出力

- <書き出すファイルの絶対パス (tmp/<作業名>/ 配下、または編集するリポジトリのファイル)>

## 範囲

- やること
  - <...>
- やらないこと
  - <...>
- すでに分かっていること・除外したこと・合意済みの方針
  - <...>

## 守ること

- リポジトリの規約 (CLAUDE.md、lint や formatter の設定) に従う
- コミット・push・issue / PR への書き込みはしない。必要なら文面の下書きを出力ファイルに書く
- 設計の判断が要る点は自分で決めず、報告の「判断を仰ぎたい点」に書く。合意済みの方針で答えが決まるものは判断事項にせず、方針に従う
- サブエージェントを起動しない。レビューは指揮役が別に起動するので、作業役が起動すると重複し、指揮役から見えない利用量も増えるため
- コマンドは `&&`・`;`・パイプで連結せず、1 つずつ実行する。承認を求めるプロンプトはこの依頼の文脈なしで人間に届くので、1 つのコマンドにして人間が中身を読んで判断できるようにする

## 報告

調べた経過や根拠の詳細は <tmp/<作業名>/report-<名前>.md の絶対パス> に書き出し、最終応答では次の項目だけを短く返してください。

- 作成・変更したファイル
- 読んだファイルと、範囲内だが読んでいないファイル
- 確認した事実と、確認していない項目 (「未確認」と書く)
- 判断を仰ぎたい点
```

### 4. 作業役の報告を検査する

作業役の報告はそのまま採らない。サブエージェントも誤り、その誤りは確信のある口調で返ってくるため。採る前に、少なくとも次のどれか 1 つを自分で確かめる。

- 根拠にしたファイルを 1 つ開き、報告と突き合わせる
- 件数や行数を `wc` や `grep -c` で取り直す
- テストを自分で再実行する

合わない点は `tasks.md` の判断の記録に書き、作業役に差し戻す。同じ点で 3 回差し戻しても直らなければそれ以上は差し戻さず、人間への報告の「判断を仰ぎたい点」に回す。手順 5 のレビューの指摘を直させるときも同じにする。繰り返しても直らないのは作業役に渡した情報か方針に問題があるときで、差し戻すたびに指揮役の利用量もかかるため。

### 5. レビューさせる

成果がそろったら、作業役とは別にレビュー役を 1 体起動する。指揮モードで起動したことをセルフレビューの指示として扱うので、人間の指示を待たずに起動してよい。起動の仕方 (`model` と `fork`) は作業役と同じ。

- 依頼文は `self-review` スキルの雛形を使う。「この変更が満たすべき要件」には、人間の元の指示と完了条件を入れる
- 出力先は、`self-review` スキルの「スクラッチパッドに置く」に代えて `tmp/<作業名>/review-<対象>.md` にする。同名のファイルがあれば `-2`、`-3` と連番を付け、再レビューの前後の結果を残す
- `tmp/` 配下の成果物は git に無視されて差分に出ないので、雛形の「未追跡の対象ファイル」に絶対パスで並べる。`tasks.md` と作業役の報告ファイル (`report-*.md`) は作業の経緯なので渡さない
- 作業の意図や経緯は渡さない。レビュー役が作業役の判断を追認する方向へ引きずられるため
- 成果物がコードでないとき (文書や下書き) は、評価の観点を成果物に合わせて置き換える

レビュー結果のファイルを読み、指摘ごとに「対応する」「対応しない」「判断を仰ぎたい」を決めて、理由を 1〜2 文で `tasks.md` の判断の記録に書く。

- 「対応する」指摘は SendMessage で作業役に直させ、直した箇所を指揮役が確かめる。担当が指揮役のタスクへの指摘は、指揮役が自分で直す
- 「判断を仰ぎたい」指摘は直さず、人間への報告に回す
- 成果物を大きく書き直すことになる指摘は、「対応する」と思っても「判断を仰ぎたい」に回す。大きな書き直しの前には人間の見解を聞くため

[must] か [should] の指摘に対応して成果物が変わったときだけ、新しいレビュー役を起動して再レビューさせる。前回のレビュー役に頼むと、自分の指摘が直ったかだけを見る方向に偏るため。それ以外の指摘への対応では再レビューしない。

再レビューの依頼文には前回のレビュー結果のファイルのパスを添え、各指摘が直ったかの確認と、成果物全体を新しく見ることを分けて頼む。指揮役の判断 (「対応しない」とした指摘とその理由) と作業の経緯は渡さない。直っていない指摘や退けた指摘がもう一度挙がれば、指揮役の判断を見直すきっかけになるため。

`self-review` スキルは見解を示したところで止める決まりだが、指揮モードでは「対応する」と決めた指摘はそのまま直してよい。判断の内容は手順 6 で人間に報告するため。

### 6. 人間に報告する

完了条件を満たしたとき、または判断を仰ぐ点が出て先に進めなくなったときに報告する。報告には次の 4 つを必ず含める。

1. 結論
   - 完了条件を満たしたか
   - 作成・変更したファイルと `tasks.md` の絶対パス
   - リポジトリのファイルを変更したときは `git diff` の差分と、`git status --porcelain` で見つけた未追跡の新規ファイルの絶対パス。`git diff` には未追跡のファイルが出ないため
2. レビューの指摘と、指揮役の判断
   - No. / 指摘の要約 / 判断 / 理由 の表と、レビュー結果のファイルのパス
   - 「対応しない」と決めた指摘も省かない。指揮役とサブエージェントの間で閉じた判断の妥当性を、人間が検査できるようにするため
3. 検査したこと
   - 作業役の報告を何でどう確かめ、結果はどうだったか
   - 確認していない項目
4. 判断を仰ぎたい点
   - 一覧にとどめ、このターンでは問いかけの形にしない
   - 作業役・レビュー役が挙げた判断事項をそのまま並べない。指揮役が次の 2 つを確かめ、判断が要るものだけを残す
     - 合意済みの方針 (既存の振る舞いを変えない、など) で答えが決まっていないか。決まっていれば判断事項にせず、方針に従って成果物に反映させ (作業役が反映していなければ差し戻す)、`tasks.md` の判断の記録に書く
     - 事実の裏付けがあるか。「不具合」「使われていない」のような言い切りは、本番の挙動やデフォルトブランチのコードのような一次資料で確かめてから書く。手元環境で観測した結果を、一次資料の振る舞いとして書かない。確かめられなければ、言い切らずに未確認と書いて残す
   - 残した判断事項には、何を決めてほしいかと、その理由・裏付けを 1〜2 文で添える。背景の説明から入らず、判断事項を先に書く。人間は作業の細部を追っていないので、どちらを選ぶと何が変わるかに絞る

報告の後に人間から成果物への指摘を受けたら、評価と修正案を示すところで止め、同意を得てから作業役に直させる。グローバル指示の手直しの規則は、指揮モードでもそのまま適用するため。

## 利用量を抑えるために

- 起動するのは、タスクごとの作業役 1 体と、成果全体へのレビュー役 1 体を基本にする
- 数回のツール呼び出しで済む作業は依頼せず、指揮役が自分で行う。依頼文を書いて報告を検査する手間のほうが大きいため
- 指揮役は作業役の成果物を全文読み込まず、検査と判断に必要な箇所だけを読む。レビュー結果のファイルは全文読む
