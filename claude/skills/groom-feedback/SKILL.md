# Groom Feedback

## 目的

フィードバックはメモリに溜まる一方、本来の格納先 (スキル・CLAUDE.md・hook) に反映されないと二重管理になり、同じ指摘が繰り返される。このスキルは全プロジェクトのフィードバックメモリを横断で棚卸しし、格納先へ反映してズレを解消する。

起動したプロジェクトに依存しない。すべてのプロジェクトの memory を対象にする。

## 前提

- dotfiles 由来のスキルは、`~/.claude/skills/` から dotfiles (`~/.dotfiles/claude/skills/`) へのシンボリックリンクとしてインストールされている。スキルを新規作成するときは dotfiles 側に作り、`setup/claude.sh` を実行してリンクを張る
- このスキルはサブエージェントを使わず、起動したセッション自身が収集・判定・反映案の作成を行う。この作業のほぼすべては格納先の判定で、判定を別のエージェントに渡すと根拠を検査できないうえ、同じメモリと設定を読み直す分だけ利用量が増えるため
- 作業ファイルは `~/.dotfiles/tmp/groom-feedback/` に置く。書く前に `git check-ignore tmp/groom-feedback/feedback-inventory.md` で無視されることを確かめ、無視されていなければ conductor スキルの「作業場所を用意する」と同じ手順で `tmp/.gitignore` を置く

## 手順

1. **対象を絞る**
   - `~/.claude/projects/*/memory/` 配下の `metadata.type: feedback` を持つメモリを列挙する
   - 各メモリの frontmatter に前回の棚卸しの記録 (`metadata.groomed` と `metadata.groom_result`) があるか見る。次のものだけを今回の対象にする
     - 記録がないメモリ
     - `metadata.modified` が `metadata.groomed` より後のメモリ。`modified` はメモリツールが書いたときに付くタイムスタンプで、Bash や Edit で書いても付かないので、`modified` がなく記録があるメモリは未変更とみなす
   - 対象外のメモリは、前回の判定を引き継ぐ。一覧には題名と前回の判定だけを載せ、判定し直さない
   - プロジェクトをまたいで同じ主題のメモリはまとめて 1 件として扱う。まとめた中に判定済みのメモリがあれば、その判定を引き継ぎ、今回の対象のメモリで判定が変わるかだけを確かめる

2. **格納先を判定する**
   - グローバルかプロジェクトかは、規則の内容がそのプロジェクトの事情 (リポジトリの構成、チームの慣習、特定のツールやテンプレート) に依存するかどうかで決める。指摘が出たプロジェクトや回数では決めない。依存しない規則は、1 プロジェクトで 1 回出た指摘でもグローバルに入れてよい
   - 依存しない規則の格納先
     - 機械的に判定できる (文字の規則、禁止するパターン) → hook や textlint の検査。文章の規則は読み落とされることがあるが、検査は毎回働くため
     - 特定スキルの挙動に関する指摘 → そのスキル
     - 繰り返し現れる手順・作法で、既存スキルのどれにも当てはまらない → 新しいスキルの候補。スキルを新しく作るときだけは繰り返しを根拠にし、1 件だけの指摘では作らない
     - それ以外 → グローバル CLAUDE.md
   - 依存する規則の格納先
     - チームで共有すべき規則 → そのプロジェクトの CLAUDE.md。別リポジトリなので、反映には PR が要る
     - 本人だけの作法 → メモリのまま
   - セッション固有・一時的なもの → メモリのまま
   - 判定ごとに理由を 1 文で書く。理由に「〇〇固有」と書いた判定の格納先がグローバルになっていたら、どちらかが誤っているので判定し直す

3. **未反映と矛盾を検出する**
   - 判定した格納先に既に反映されているか確認する。反映済みなら触らない
   - 対象のメモリのうち、CLAUDE.md・スキルと矛盾するものと、存在しないファイルやメモリを指すものを洗い出す

4. **一覧をファイルに書く**
   - 手順 1〜3 の結果 (全メモリの一覧、判定と理由、反映状況、矛盾と存在しない参照) を `~/.dotfiles/tmp/groom-feedback/feedback-inventory.md` に書く。件数に関係なく、一覧はチャットに貼らずファイルに書く
   - チャットには、対象にした件数と、反映案の題名の一覧だけを出す
   - 反映案が 5 件以上あるときは、このターンを質問だけにして、どれから見るか・見送るかを選んでもらう

5. **反映案を 1 件ずつ提示する**
   - 1 ターンに 1 件、変更前・変更内容・これで変わることの 3 点で示し、承認を待つ。変更後の文が 2〜3 文に収まるなら全文を示す
   - 案の種類
     - 既存スキル・CLAUDE.md への追記・修正
     - 新しいスキルの新規作成 (`anthropic-skills:skill-creator` を使う。名前はユーザーに候補を出して選んでもらう)
     - hook や textlint の検査の追加・修正 (`~/.dotfiles/claude/hooks/`・`~/.dotfiles/claude/textlint/`)
   - 承認された案はそのターンで編集し、差分を報告して止める。次の案は次のターンで出す

6. **スキル変更時は検証する**
   - スキルを新規作成・変更した場合は `anthropic-skills:skill-creator` で旧版スナップショット (新規なら未使用時) と新版に同じ入力を流し、退行や過剰反応がないか確認する
   - 変更が軽微なら省略してよい

7. **コミットする**
   - dotfiles のスキル・CLAUDE.md・hook・textlint の設定を編集していれば、dotfiles リポジトリで commit スキルに従ってコミットする

8. **判定を記録し、メモリを後始末する**
   - 今回判定したメモリすべての frontmatter に、`metadata.groomed` (判定した日時。`modified` と同じ ISO 8601 の UTC 形式) と `metadata.groom_result` (格納先と理由を 1 文) を書く。次回の棚卸しで判定し直さないため
   - 恒久先へ完全に吸収され、単独のリマインダーとして不要になったメモリは削除する。参照価値が残るものは残す
   - 矛盾するメモリと存在しない参照を持つメモリは、承認を得てから削除するか更新する
   - 各プロジェクトの `MEMORY.md` の索引を更新する

## 注意

- 全フィードバックがスキル行きではない。手順 2 の判定を飛ばさない
- 反映は最小限・具体的に。スキル本体を肥大化させない
- ユーザーの承認前に、スキル・CLAUDE.md・hook を編集しない。メモリへの判定の記録は承認なしで書いてよい
