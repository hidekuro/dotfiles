# issue 作成

issue の読者はチームのメンバーと、後でこの issue を読む AI エージェントの両方。人間が一目で「何をするか」を掴める本文と、後続の作業に必要な詳細を分けて書く。

issue / PR に共通する規則 (本文の先頭に注意書きを置く、書き込み前に承認を得るなど) はグローバル CLAUDE.md の「GitHub の issue / PR」節に、他者に出す資料に共通する規則 (ローカルパスを書かないなど) は同「文章の書き方」節に従う。

## 手順

### 1. 情報を集める

- 作成先リポジトリ (`<owner>/<repo>`) を確定する。カレントディレクトリのリポジトリとは限らない
- 作成先の issue テンプレートを `.github/ISSUE_TEMPLATE/` で探す。Markdown のテンプレートなら構成を合わせ、YAML form (`*.yml`) なら各フィールド (`id`) に対応する内容を用意してから本文を組み立てる。テンプレートに合わせるときも、「書き方」の骨組みにある注意書き・きっかけのリンク・AI 向けの `<details>` は残す
- 作成先の organization に issue types (Bug / Feature / Task など) があれば、作成時に type を付ける。types があるときは、ラベルの `bug` や `enhancement` で代用したり、タイトルに `[Bug]` のような接頭辞を付けたりしない。分類が二重になるため。次のコマンドが失敗したら (ユーザー所有のリポジトリなど)、types なしとして扱う

  ```bash
  gh api orgs/<owner>/issue-types --jq '.[].name'
  ```

- 同じ内容の issue を探す。重複した issue を作ると、議論と進捗が 2 か所に分かれるため

  ```bash
  gh issue list --repo <owner>/<repo> --search '<キーワード>' --state all
  ```

- 機能の要望なら、その挙動がコードに既にないかも確かめ、調べた場所を AI 向けの文脈情報に書く。実装済みの機能を起票しないため
- 親 issue の有無と、きっかけになったもの (問い合わせ・アラート・会話のログなど) のリンクを会話から拾う。分からなければ質問する

### 2. 下書きして見直す

- 「書き方」に従ってタイトルと本文を下書きする
- 提示する前に、下書きを「書き方」の観点で見直す。あわせて、ローカルパスが含まれていないかを確かめる

### 3. 提示して承認を待つ

タイトル・本文の全文・作成先リポジトリ・issue type・親 issue (あれば sub-issue として紐付けること)・重複の候補 (見つかったときだけ) を提示し、承認を待つ。

### 4. 作成する

- 本文をスクラッチパッドのファイルに書き出す
- 次のコマンドで作成する。タイトルを単一引用符で囲むのは、タイトル中の `$` やバッククォートをシェルに展開させないため

  ```bash
  gh issue create --repo <owner>/<repo> --title '<タイトル>' --body-file <パス>
  ```

  - issue types があれば `--type <名前>` を付ける
  - 親 issue があれば `--parent <親の番号>` を付ける。親が別リポジトリなら番号ではなく URL を渡す
  - ラベル・担当者・Project・マイルストーンは、ユーザーが指定したときだけ付ける
- 作成した issue の URL を報告する

## 書き方

### タイトル

- 「何をするか」が分かる簡潔な文にする
- まだ確定していない原因 (推測) を入れない。原因が否定された後も issue 一覧・通知・他所からのリンクにタイトルが残って誤った原因が広まり、読み手の調査や議論もその原因の確認に偏るため
- 「〜になっている」のようなストーリー形式にこだわらない

### 本文

- 注意書きの直後に、きっかけになったもののリンクを置く。読み手が AI の要約より先に一次情報を確かめられ、対応後にきっかけの問い合わせやスレッドへ結果を返す入口にもなるため
- 人間向けの部分は箇条書きで短くする。横に長い段落を避ける
- ただし削りすぎない。「何が」「どうなった」が抜けると意味が通じなくなるので、1 項目に主語と結果を書き切る
- 優先度や温度感は、ユーザーが求めない限り書かない。優先度はチームの場で決めるもので、書くと読み手が事実から重さを判断する前に温度感に引っ張られるため
- 解釈 (「人間の操作だった」など) を事実として書かない。確認した事実を書いたうえで「可能性が高い」と結ぶ
- タスクの issue (事象の報告ではなく、やることを決めた issue) には、完了と判定する条件を `- [ ]` のチェックリストで書く。担当者や後続のセッションが、終わったかを本文だけで判断できるようにするため
- 集計値・クエリ・コード解析などの詳細は、末尾の AI 向けの文脈情報に畳む。後続のセッションで AI が使う記録で、人間が読む成果物ではないため

本文の骨組み:

```markdown
> [!NOTE]
> この注意書きが残っているあいだは、Claude (<モデル名>) が書いた本文を hidekuro が確認しています

<きっかけのリンク>

- <何が> <どうなった>
- ...

完了条件 (タスクの issue のときだけ):

- [ ] <完了と判定する条件>

---

<details>
<summary>以下、AI 向けの文脈情報 (YYYY-MM-DD 時点)</summary>

<集計値・クエリ・コード解析>

</details>
```

### sub-issue

本文に「親 issue: #NNN」と書くだけでは、親 issue の進捗表示や Project のツリー表示に反映されない。作成時に `--parent` で紐付ける。既存の issue を後から紐付けるときは `gh issue edit <子の番号> --parent <親の番号>` を使う。作成時と後から紐付けるときのどちらでも、`gh` が `--parent` に対応していなければ REST API で設定する (作成時は、親を付けずに作成してから設定する)。

```bash
gh api repos/<owner>/<repo>/issues/<子の番号> --jq '.id'
gh api --method POST repos/<owner>/<repo>/issues/<親の番号>/sub_issues -F sub_issue_id=<上で得た id>
```
