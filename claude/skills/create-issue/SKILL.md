# issue 作成スキル

issue の読者はチームのメンバーと、後でこの issue を読む AI エージェントの両方である。人間が一目で「何をするか」を掴める本文と、後続の作業に必要な詳細を分けて書く。

issue / PR に共通する規則 (本文を HTML コメントで囲む、ローカルパスを書かない、書き込み前に承認を得るなど) は、グローバル CLAUDE.md の「GitHub の issue / PR」節にすべて従う。

## 手順

1. 情報を集める
   - 作成先リポジトリ (`<owner>/<repo>`) を確定する。カレントディレクトリのリポジトリとは限らない
   - 作成先リポジトリに issue テンプレートがあれば、構成をそれに合わせる
   - 親 issue の有無、きっかけになったもの (問い合わせ・アラート・会話のログなど) のリンクを会話から拾う。分からなければ質問する
2. タイトルと本文を下書きする (次節の作法に従う)
3. 提示する前に、下書きを「書き方」節の観点で見直す。あわせて、ローカルパスと `-->` が含まれていないかを確認する (`-->` があると、本文全体を囲む HTML コメントがそこで閉じる)
4. タイトル・本文の全文・作成先リポジトリ・親 issue (あれば sub-issue として紐付けること) を提示し、承認を待つ
5. 承認後、本文をスクラッチパッドのファイルに書き出して作成する
   - `gh issue create --repo <owner>/<repo> --title '<タイトル>' --body-file <パス>`。タイトルを単一引用符で囲むのは、タイトル中の `$` やバッククォートをシェルに展開させないため
   - 親 issue があれば `--parent <親の番号>` を付ける。親が別リポジトリなら番号ではなく URL を渡す
   - ラベル・担当者・Project・マイルストーンは、ユーザーが指定したときだけ付ける
6. 作成した issue の URL を報告する

## 書き方

### タイトル

- 「何をするか」が分かる簡潔な文にする
- まだ確定していない原因 (推測) を入れない。原因が否定された後も issue 一覧・通知・他所からのリンクにタイトルが残って誤った原因が広まり、読み手の調査や議論もその原因の確認に偏るため
- 「〜になっている」のようなストーリー形式にこだわらない

### 本文

- 冒頭に、きっかけになったもののリンクを置く。読み手が AI の要約より先に一次情報を確かめられ、対応後にきっかけの問い合わせやスレッドへ結果を返す入口にもなるため
- 人間向けの部分は箇条書きで短くする。横に長い段落を避ける
- ただし削りすぎない。「何が」「どうなった」が抜けると意味が通じなくなるので、1 項目に主語と結果を書き切る
- 優先度や温度感は、ユーザーが求めない限り書かない。優先度はチームの場で決めるもので、書くと読み手が事実から重さを判断する前に温度感に引っ張られるため
- 解釈 (「人間の操作だった」など) を事実として書かない。確認した事実を書いたうえで「可能性が高い」と結ぶ
- 集計値・クエリ・コード解析などの詳細は、末尾の AI 向けの文脈情報に畳む。後続のセッションで AI が使う記録で、人間が読む成果物ではないため

本文の骨組み:

```markdown
<!--
<きっかけのリンク>

- <何が> <どうなった>
- ...

---

<details>
<summary>以下、AI 向けの文脈情報 (YYYY-MM-DD 時点)</summary>

<集計値・クエリ・コード解析>

</details>
-->
```

### sub-issue

本文に「親 issue: #NNN」と書くだけでは、親 issue の進捗表示や Project のツリー表示に反映されない。作成時に `--parent` で紐付ける。既存の issue を後から紐付けるときは `gh issue edit <子の番号> --parent <親の番号>` を使う。作成時と後から紐付けるときのどちらでも、`gh` が `--parent` に対応していなければ REST API で設定する (作成時は、親を付けずに作成してから設定する)。

```bash
gh api repos/<owner>/<repo>/issues/<子の番号> --jq '.id'
gh api --method POST repos/<owner>/<repo>/issues/<親の番号>/sub_issues -F sub_issue_id=<上で得た id>
```
