# PR 作成

## 目指すもの

PR 本文の読者はレビュアーで、差分はすでに読める。「○○関数を追加した」のような差分の言い換えには価値がなく、本文に書く価値があるのはコードから読み取れない文脈だけ。

- なぜこの変更が必要だったのか (動機・背景)
- どういう判断でこのアプローチを選んだのか
- どの範囲に影響があるか
- 何を検証済みで、何を検証していないか

## 手順

### 1. 情報を集める

次を 1 行ずつ単独のコマンドとして、並列に実行する。`@{upstream}` が失敗したら upstream なしと判断する。

```bash
git branch --show-current
git status --short
git rev-parse --abbrev-ref @{upstream}
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
gh pr list --head <current> --state open --json number,url
```

次のときは作成に進まず、ユーザーに伝える。

- カレントブランチがデフォルトブランチ
- 未コミットの変更がある。`git status` の結果を示してコミットを促す
- このブランチの open な PR がすでにある。URL を示す。本文の更新は別の依頼として扱う。`--state open` で絞るのは、同じブランチ名で過去に閉じた PR があっても新しく作れるようにするため

続いて、ベースブランチ名とカレントブランチ名をリテラルで埋めて、差分とコミット履歴を取る。コミットが 0 件なら作成を中止して伝える。

```bash
git diff --stat <base>...<current>
git log <base>..<current> --pretty=format:"%H%n%s%n%b%n---" --reverse
```

変更ファイルが 20 を超えるような大きな差分では、`git diff --stat` で概要を掴み、主要なファイルだけ `git diff` で読む。

### 2. リポジトリの規約を確かめる

PR テンプレートを次の順に探し、見つかったら読む。

1. `.github/pull_request_template.md`
2. `.github/PULL_REQUEST_TEMPLATE.md`
3. `.github/PULL_REQUEST_TEMPLATE/*.md`
4. `docs/pull_request_template.md`
5. `pull_request_template.md` (リポジトリ直下)

`.github/PULL_REQUEST_TEMPLATE/` に複数あるときは、変更の性質 (バグ修正、機能追加など) に合うものを選び、選べなければユーザーに聞く。

`CONTRIBUTING.md` (直下か `.github/`) があれば、PR タイトルの命名規則 (conventional commits など)・必須のチェック項目・言語の指定を読む。

### 3. 差分から意図と影響を読む

本文の質はここで決まる。コミットメッセージと差分を突き合わせる。

- コミットが 1 件ならそれが主旨。複数なら共通するテーマを取り出す。`fix`・`wip`・`typo` のような雑なメッセージは当てにせず、差分で判断する
- 整ったメッセージの主張 (「既存のパターンに合わせた」など) も鵜呑みにせず、該当するコードを開いて確かめてから本文に書く。誤った主張がそのままレビュアーに届くため
- 差分の種類ごとに読むこと
  - テストの変更: どんな振る舞いが保証されたか
  - 設定ファイル: デプロイや環境への影響。本文に明記する
  - スキーマ・マイグレーション: データ構造への影響。特に注意して書く
  - 依存関係: 追加・削除・更新の理由
  - ファイルの移動・削除: 既存コードへの影響範囲
- 変更の性質 (新機能 / リファクタリング / バグ修正 / 設定変更) を決める。無関係な変更が混在しているなら、それぞれに簡潔に触れる
- 影響範囲は差分のパスから特定する。インフラ・デプロイの設定と DB は影響範囲として明記する。テストコードは影響範囲に数えない

### 4. タイトルを決める

- 70 文字以内で、PR の一覧に並んだときに意味が伝わる文にする (「Update files」は不可)
- 変更の結果として何が実現されるかを書く。複数の変更が混在するなら、最も影響が大きいものを主題にする
- `git log --oneline -20` で conventional commits (`feat:`、`fix:` など) が使われていれば、タイトルにも付ける
- 日本語か英語かは、CONTRIBUTING の指定か、リポジトリの言語の文脈で決める

### 5. 本文を書く

本文の先頭には、グローバル CLAUDE.md の「GitHub の issue / PR」節の規則に従って注意書きを置く。その節にはリポジトリの規定の注意書きを使う例外があるので、PR テンプレートと、テンプレートから参照される AI 向けのガイドラインに規定がないかを確かめる。

テンプレートがあるとき:

- 全セクションを埋める。見出しと順序はテンプレートのままにする
- 該当しない節は消さず、「該当なし」と、検討したことが分かる 1 句 (例:「DB の変更なし」) を書く。テンプレート自身が不要な節を消すよう案内しているときは、それに従う
- `<!-- -->` の記入方法の案内は消さず、その下に本文を書く
- チェックリスト (`- [ ]`) にはチェックを付けない。ユーザーが確かめてから付ける
- テンプレートにないことは足さない

テンプレートがないとき:

- 設定の変更や数行の修正のような小さな変更では、見出しを立てずに変更の動機を 1〜2 文で書く (先頭に注意書きを置くのは同じ)。節を埋めようとすると、差分を読めば分かることを書き足すことになるため
- それ以外は次の構造にする

```markdown
> [!NOTE]
> この注意書きが残っているあいだは、Claude (<モデル名>) が書いた本文を hidekuro が確認しています

## 概要

<なぜこの変更が必要だったのか。解決する問題・実現したい目的を 2〜4 文で>

## 変更内容

- <採用したアプローチの選択理由や、コードからは読み取れない判断>

## 影響範囲

<影響するシステムの範囲。特に DB・インフラ・外部 API など注意が必要な箇所>

## テスト

- <実行して確かめたこと>

## 関連 Issue / PR

<あれば記載。なければセクションごと削除>
```

書くこと:

- 変更の動機 (なぜ今これが必要か)
- アプローチの選択理由 (ほかの選択肢があった場合)
- レビュアーに特に見てほしい点
- 既知の制約・TODO・リスク
- テスト欄には、実行して確かめたことだけを書く。実行していない確認を確認済みのように書くと、レビュアーが確認済みだと受け取るため
  - 走らせていない確認は「未実行」と、走らせるべきコマンドを書く
  - CI が結果を出す項目は、観察ではなく期待として書く (「CI で〇〇のテストが通ること」)
- 関連 issue は対象の issue だけを書く。PR が issue を完全に解決するときだけ閉じるキーワード (`Fixes #N` など) を使い、部分的な対応や不確かな番号には付けない。マージで issue が意図せず閉じるため

書かないこと:

- コードを見れば明らかなこと (「〇〇メソッドを追加した」「△△を削除した」)
- ファイル名の羅列
- コミットログのコピー
- AI 固有の言い回し (「タスク 1」「フェーズ A」「ステップ 1」など)
- テスト / 動作確認の欄に、狙った効果が出たかの測定や、再現コマンド列・対照実験の詳細。書くのは「変更が対象環境に適用され、その状態で壊れていないこと」の確認だけ。効果測定は issue 側のタスクに切り出す
- 関連 Issue / PR の欄に、参考にした PR や似た前例の PR。前例を踏襲したことは地の文で 1 文触れる
- レビュアーがすでに知っている運用の説明 (例:「prod の Environment には required reviewers があるので、承認待ちで止まる」)。そのリポジトリで作業する人には自明で、本文を長くするだけのため

文体は「である調」 (「追加した」「修正した」) か英語で統一する。CONTRIBUTING の指定があればそれに従う。

下書きができたら、段落 (箇条書きなら項目) ごとに「レビュアーのどの判断を助けるか」を問い、答えられない段落は消す。差分を見れば分かること、差分が足したコメントの言い換え、同じ事実の 2 回目は、この問いで落ちる。

### 6. ユーザーに確かめる

ドラフト PR なら、レビュー依頼が届く前にユーザーが PR 上で本文を確かめられるので、確認はタイトルだけにする。ドラフトではない PR を求められたときは、作成と同時に本文がレビュアーに届くので、タイトルとあわせて本文の全文を提示して承認を得る。

```text
以下のタイトルで PR を作成します。

**タイトル:** [生成したタイトル]
**ベースブランチ:** [base] ← [current]
**種別:** ドラフト PR (通常 PR にする場合はその旨お知らせください)

よろしければ「OK」または「作成して」と返信してください。
タイトルを変えたい場合はご指示ください。
```

修正の要望が来たら直して再提示し、明示的な承認が出るまで作成しない。

### 7. PR を作成する

- upstream がなければ `git push -u origin <current-branch>` で push する
- 本文を Write ツールでスクラッチパッドのファイルに書き出す
- 次のコマンドで作成する

  ```bash
  gh pr create --title "<タイトル>" --body-file <本文ファイルの絶対パス> --base <base-branch> --assignee @me --draft
  ```

  - `--assignee @me` は常に付ける (作成者を自動でアサイン)
  - `--draft` は既定。ユーザーが「ドラフトではない」と明示したときだけ省く
  - `--reviewer`・`--label` はユーザーが指定したときだけ付ける
- 作成したら PR の URL を示す

エラーのとき:

- `gh` が未認証 → `gh auth login` の実行を促す
- ベースブランチが存在しない → 正しいベースブランチをユーザーに確認する

## 守ること

- PR 作成後の操作 (マージ、レビュアーの割り当てなど) は、明示的な指示があったときだけ行う
- 人間が清書した本文で削られた内容の復活を提案しない。AI の下書きは清書の材料で、削ることはレビュアーへの配慮による意図的な判断のため
