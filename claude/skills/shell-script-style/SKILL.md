# シェルスクリプトの書き方

## 目指すもの

シェルスクリプト、とくに CI 補助や運用の検証スクリプトは、書いた人がいなくなった後も長く放置され、文脈を持たない人が読む。読み手は「そのファイルを上から順に読めば分かる」ことを期待している。シェルの凝った技で短く書くより、線形で明示的に書く方が保守できる。

前提として、スクリプト冒頭で `set -e` (bash なら `set -euo pipefail`) を有効にし、shellcheck を通す。以下の方針はこの前提の上で成り立つ。

コメントの方針は CLAUDE.md の「コードコメント」節、ヘルパー関数の方針は同「コードの書き方」節に従う。

## 線形で明示的な書き方を選ぶ

- 複数のコマンドの出力をまとめてパイプに流す形 (`{ cmd1; cmd2; } | cmd3`) は、一時ファイルを挟んで 2 段に分ける。中間結果が目に見える方が追いやすい
- `set --` で argv を可変構築しない。常に同じ引数を渡せる形に揃える (例: 省略時のデフォルト値 `${duration:-0s}` を使う)
- ヘルパー関数が必要なら同一ファイル内に置く。`lib.sh` のような共有ファイルに切り出すと、本体を読むために別ファイルの精読が必要になる。1 行の処理を包むだけの関数 (`contains()` 等) は作らず、呼び出し側に展開する
- `awk` は `print` 中心で使う。`NR` / `NF` / 複合条件 (`NR>1 && $1!="" && $1!~/^#/`) は読み手の負担になる。「ヘッダー行を飛ばす」は `tail -n +2` のように単機能ツールで表現する
- 単純な CLI で完結する検証はコマンドを平坦に並べる。`set -e` で失敗が自明なら `fail "..."` のようなメッセージ出力を重ねない
- タスクランナー → スクリプト → 別ツールのような多段の間接呼び出しを作らない。呼び出し元のスクリプトから別のスクリプトを呼ぶ構成も、必要な段数まで減らす

## 冪等な CLI では事前チェックを省く

`add` / `remove` が冪等な CLI を使うなら、「存在確認 → 操作」の事前チェックは書かない。冪等性で済むものを条件分岐にすると、分岐の数だけ読み手の負担が増える。差分計算が本当に必要なのは「逆方向の削除 (実環境にあって入力データにないものを消す)」のような、CLI が代わりにやってくれない部分だけであることが多い。

## 対象の増減はデータ側で行う

シナリオ一覧・許可リストのような増減する対象は、for 文の入力リストをスクリプト内で編集させず、fixture ファイル (データ) 側で増減させる。検証は「コマンド → 正規化 → コミット済み fixture と diff」の形に統一すると、失敗時の diff 出力だけで原因が分かる。

複雑な grep や、対象の増減でロジック改変が要る状態になったら、シェルにこだわらず別ツール (go test 等) を検討する。ただし、新しい言語やテスト基盤を持ち込むのと、リポジトリに既にあるものを使うのは別の判断で、後者を優先する。

## 書かないテスト

- 同語反復のテスト。「YAML に `capacity: 50` と書いてある」ことの検証は値の複製にすぎず、何も保証しない。閾値は上限を超えたときの挙動で検証するか、CI では見ない
- 中途半端に一部だけを対象にするテスト。「これは対象か否か」の判断に文脈が要る状態は、後から読む人が判断できない。全部やるか全部やらないかの均一なルールにする

## 入力仕様を勝手に広げない

スクリプトが扱う入力データの仕様について、「〜でも十分安全そう」のような評価的な発言を「〜という要件」に拡大解釈しない。例: 「カンマが最後の列にある CSV は単純 split でも安全」は「値にカンマを生で書ける仕様」を意味しない。仕様が曖昧なら補完せず、その場でユーザーに確認する。

## 書き終えたら見直す

1. 上から順に読んで、別ファイルや別コマンドの精読なしに処理が追えるか
2. 条件分岐のうち、CLI の冪等性やデフォルト値で消せるものはないか
3. 1 行しかない関数、`print` 以外の awk、複数コマンドをまとめて流すパイプが残っていないか
4. 対象を増やすときにスクリプト本体を編集する必要があるか (あるならデータ側へ移せないか)
5. ユーザーが明示していない入力仕様を自分で足していないか
